## Why the current build can't connect to claude.ai

Our hosted MCP passes credentials as `?gh_token=...&api_key=...` in the URL.

> "Tokens or API keys passed in the connector URL (for example, `?token=`, `?apiKey=`, or `?userToken=` query parameters) are **not recommended**. A credential in a URL is a security vulnerability… The MCP authorization specification explicitly prohibits access tokens in the URI query string."
> — [Claude connector auth docs](https://claude.com/docs/connectors/building/authentication)

> "Access tokens **MUST NOT** be included in the URI query string"
> — [MCP spec, Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

When you paste our URL, Claude ignores the query params and starts an OAuth handshake:
1. Expects `401` + `WWW-Authenticate: Bearer resource_metadata="…"`
2. Fetches `/.well-known/oauth-protected-resource`
3. Reads `authorization_servers` → fetches that server's `/.well-known/oauth-authorization-server`
4. Registers itself (DCR) → runs auth-code + PKCE → gets a Bearer token

We serve none of those. Hence: *"Couldn't register with teamctx's sign-in service."*

## What Claude actually supports (verified)

Six auth types, from the [official table](https://claude.com/docs/connectors/building/authentication):

| Type | Availability | Fits us? |
| --- | --- | --- |
| `oauth_dcr` — OAuth 2.0 + Dynamic Client Registration | **Out of the box** | ✅ yes |
| `oauth_cimd` — OAuth 2.0 + Client ID Metadata Document | Out of the box | ✅ alternative to DCR |
| `oauth_anthropic_creds` | Email `mcp-review@anthropic.com` | ⚠️ needs Anthropic approval |
| `custom_connection` | Contact Anthropic | ⚠️ needs approval |
| `static_headers` — fixed API key/bearer in a header | **Beta — "contact Anthropic for early access"** | ⚠️ gated, and org-wide not per-user |
| `none` — authless | Supported | ✅ for single-tenant deploys |

Two things I got wrong earlier and am correcting:

- **GitHub OAuth cannot be our authorization server.** GitHub does not expose `/.well-known/oauth-authorization-server` (RFC 8414), a `/register` endpoint (RFC 7591), or protected resource metadata (RFC 9728). Verified against [GitHub's OAuth docs](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps). GitHub can only be the **identity provider** behind our own AS.
- **Claude Desktop is not a shortcut.** Claude.ai web, Desktop, mobile, Claude Code and Cowork all share the same connector infrastructure. There is no header-based back door for remote URLs outside the gated `static_headers` beta.

## What the MCP SDK already gives us (verified on disk)

`node_modules/@modelcontextprotocol/sdk@1.29.0` ships a **complete OAuth 2.1 authorization server**:

```
server/auth/router.js               → mcpAuthRouter() — mounts all endpoints
server/auth/handlers/metadata.js    → /.well-known/oauth-authorization-server
server/auth/handlers/authorize.js   → /authorize
server/auth/handlers/token.js       → /token
server/auth/handlers/register.js    → /register (RFC 7591 DCR)
server/auth/handlers/revoke.js      → /revoke
server/auth/middleware/bearerAuth.js→ Bearer validation middleware
server/auth/providers/proxyProvider.js → proxy to an upstream AS
```

`express@5.2.1` is already a transitive dependency — no new install.

We implement one interface, `OAuthServerProvider` (6 methods), and the SDK handles all HTTP plumbing, metadata documents, PKCE validation, and DCR.

## Two product models — pick one before writing code

This is a **product decision**, not a technical one, and it changes the effort by 4x.

### Model A — Single-tenant (each company deploys their own)

Each team runs their own teamctx MCP (Vercel, Docker, wherever). GitHub token and AI key live in **deployment env vars**. Auth type: `none`, or a shared secret once `static_headers` GA's.

- **Effort: ~0.5 day.** Read creds from `process.env` instead of query params; drop the query-param path.
- No KV, no OAuth, no per-user state.
- Matches how most internal MCP servers actually work, and matches teamctx's "no server, no seats, bring your own key" positioning.
- **Limitation:** one deployment = one repo + one set of creds. Not a public multi-tenant service.

### Model B — Multi-tenant (one URL, any GitHub repo, any user)

Full OAuth. Users click "Connect", sign in with GitHub, and their own credentials are used.

- **Effort: 3–4 days** (breakdown below).
- Needs Vercel KV (or Upstash) for client registrations, tokens, and per-user AI keys.
- This is what "publish teamctx to the Claude connector directory" would require.

**Recommendation: ship Model A first (half a day, unblocks the demo), then build Model B if we want a public service.** They aren't mutually exclusive — Model A's env-var path stays as the self-hosted fallback.

## Model B implementation detail

### Why GitHub must be the IdP, not the AS

Our server needs a **GitHub access token** to read/write the user's repo. If we used WorkOS/Stytch as the AS, we'd get *their* token and would still have to collect a GitHub PAT separately.

By running our own AS with GitHub as the upstream IdP, the GitHub token falls out of the authorization flow naturally — we store it in KV next to the token we mint. One flow, both problems solved.

*(WorkOS AuthKit is free to 1M MAU and does support DCR + RFC 8414 — it's a legitimate option if we ever want enterprise SSO. It just doesn't solve the GitHub-token problem, so it isn't simpler for us today.)*

### Flow

```
Claude ──POST /api/mcp/...──────────────► our MCP endpoint
       ◄─401 + WWW-Authenticate: Bearer resource_metadata="…"

Claude ──GET /.well-known/oauth-protected-resource──►
       ◄─{ resource, authorization_servers: ["https://ours"] }

Claude ──GET /.well-known/oauth-authorization-server─►
       ◄─{ authorization_endpoint, token_endpoint, registration_endpoint,
           code_challenge_methods_supported: ["S256"] }

Claude ──POST /register (DCR)──────────► store client in KV
       ◄─{ client_id }

Claude ──GET /authorize?…PKCE…─────────► we stash pending auth in KV,
                                          redirect user → GitHub
User   ──signs in at GitHub────────────►
GitHub ──GET /callback?code=…──────────► we swap for a GitHub token,
                                          mint our auth code,
                                          redirect → claude.ai/api/mcp/auth_callback

Claude ──POST /token (form-urlencoded)─► verify PKCE, mint access+refresh,
       ◄─{ access_token, refresh_token }   store {githubToken, userId} in KV

Claude ──POST /api/mcp/… + Bearer──────► verifyAccessToken → KV lookup
                                          → use stored GitHub token for repo
```

### Hard requirements (from the docs — miss any and it silently fails)

- `401` **must** carry `WWW-Authenticate: Bearer resource_metadata="…"`. Claude does **not** honor that header on a `200`.
- PRM `resource` field must match the connector URL **exactly as the user types it**, path included.
- `authorization_servers[0]` is the only entry Claude reads — no fallback to later entries.
- AS metadata must advertise `"code_challenge_methods_supported": ["S256"]`.
- `/token` must accept `application/x-www-form-urlencoded`; `/register` uses `application/json`. Different parsers.
- Redirect URI to register: `https://claude.ai/api/mcp/auth_callback`. Claude Code additionally uses loopback (`http://localhost/callback`, `http://127.0.0.1/callback`) with **port ignored**.
- Refresh tokens **must rotate** for public clients; return `invalid_grant` (not `invalid_request`) when one expires.
- **10 s timeout** on discovery/registration/token; **30 s** on refresh.
- Anthropic egress: `160.79.104.0/21` — must not be firewalled.

### Known risk

`mcpAuthRouter` is Express middleware designed to mount at an app root. Vercel serverless gives one function per file. Mitigation: a `vercel.json` rewrite sending `/.well-known/*`, `/authorize`, `/token`, `/register`, `/revoke` to a single function that runs the router. **I would spike this in the first hour** — if Express-in-serverless is painful, fall back to hand-writing the five endpoints as separate functions (more code, zero framework risk, adds ~4 h).

## What I got wrong before, plainly

1. Said "1–2 days for OAuth" — real number is 3.5–4 days for multi-tenant.
2. Said "use GitHub as the authorization server" — impossible; GitHub lacks the three required RFCs.
3. Said "Claude Desktop supports headers as a workaround" — same connector infra as web; `static_headers` is a gated beta, not a general escape hatch.
4. Didn't surface the single-tenant option, which is half a day and probably what we actually want first.
